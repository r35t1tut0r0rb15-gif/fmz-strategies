# FMZ indicator catalog

Every indicator used by the 5,806 FMZ strategies in this repo, mapped to the
best Python / vectorbt implementation we have.

Nothing here changes the strategies or `tv_indicators`. The new code lives in
staging modules that `tv_indicators` does not import. Deciding how to merge
it is the next step.

That is 241 new functions. The full table, with inputs, outputs, defaults and
sources, is in [scan/staging_functions.md](scan/staging_functions.md).
`tv_indicators` and `fmz_catalog` together pass 534 tests. Each indicator is
checked against a literal bar-by-bar port of its source (TradingView's Pine,
the published author's code, or the strategy's own code), or against TA-Lib
where TA-Lib has the same formula.

```python
import tv_indicators as ti                 # built-ins and popular scripts
import fmz_catalog.extra as fx             # staging modules
import fmz_catalog.extra_hpotter as fh

k, d, j = fx.kdj(df.high, df.low, df.close)
cfo = fh.cmo_filtered(df.close)            # every function: pandas/numpy in, same type out
```

Each staging module keeps its indicators in its own registry (`EXTRA`,
`EXTRA_TV`, `EXTRA_EHLERS`, ...) rather than in `tv_indicators.REGISTRY`. To
use one as a vectorbt class, build it with the same factory code as
`tv_indicators/vbt.py`. That gets wired up when we merge.

## Rules for "best version"

1. **TradingView built-ins:** reproduce TradingView's own Pine source exactly,
   including `na` handling and warm-up. FMZ's Pine engine documents the same
   `ta.*` formulas as TradingView.
2. **Published community or author indicators:** use the author's published
   definition (TASC articles, Ehlers' books, the original TradingView script).
   When the version everyone copies differs legitimately, it is kept as an
   option, e.g. `hpotter=True`, or `insilico_compat=True` on the sine WMA.
3. **Strategy copies with a bug:** the function computes the correct version.
   Where useful, a flag reproduces the copy. Every bug is listed in IMPACT.md
   and in `scan/impl/*_report.json`.
4. **Bespoke functions written by a single strategy author:** the strategy's
   code is the only definition, so it is ported as written and marked
   "strategy-specific" in the docstring.
5. **No look-ahead.** Pivots, fractals, divergences and ZigZag are reported on
   the bar where they become known, and each docstring states the delay.

## FMZ's own functions (JavaScript / Python / MyLanguage strategies)

These strategies call FMZ's libraries instead of Pine. When porting them,
map each call like this:

| FMZ call | Use | Note |
|---|---|---|
| `TA.MA` / `TA.SMA` / `TA.EMA` / `TA.MACD` / `TA.BOLL` / `TA.RSI` | `ti.sma` / `ti.ema` / `ti.macd` / `ti.bbands` / `ti.rsi` | Same formulas, including the SMA seed and population stdev |
| `TA.ATR` | `ti.atr` | Same from bar `period-1` on; FMZ outputs partial averages before that |
| `TA.Highest(r, n, 'High')` / `TA.Lowest` | `fx.hv_lv(...)` = `ti.highest(...)[1]` | **Excludes the current bar** |
| `TA.KDJ(r, 9, 3, 3)` | `fx.kdj` | Chinese KDJ (1/3 smoothing seeded at 50, J = 3K − 2D); not the TradingView Stochastic |
| `TA.OBV` | `ti.obv` | FMZ adds volume on unchanged closes, so its level drifts |
| `TA.CMF`, `TA.Alligator` | `ti.cmf`, `ti.alligator` | FMZ has partial windows; its Alligator arrays are longer than the bars (+8/+5/+3) |
| `talib.*` | TA-Lib itself | `talib.STOCHRSI` (no %K smoothing, default 14/5/3) and `talib.CMO` (Wilder) differ from TradingView's versions |
| MyLanguage `SMA(X,N,M)` | `fx.sma_cn` | **Not** `ta.sma`; it is Wilder-style smoothing |
| MyLanguage `HV` / `LV` | `fx.hv_lv` | Exclude the current bar |
| MyLanguage `STD` | `fx.stdev_sample` | Sample stdev (n−1) |
| MyLanguage `DMA(X,A)` | `fx.dma_cn` | Per-bar alpha |
| MyLanguage `CROSS` | vectorbt `crossed_above` | Upward only, unlike `ta.cross` |
| `REF`, `MA`, `EMA`, `HHV`, `LLV`, `SUM`, `SLOPE`, `BARSLAST`, `VALUEWHEN` | `x.shift`, `ti.sma`, `ti.ema`, `ti.highest`, ..., `ti.linreg().slope`, `fx.barssince`, `fx.valuewhen` | Partial windows at the start |

A live FMZ JavaScript bot recomputes `TA.*` on whatever bars `GetRecords`
returns. Long EMAs and RSIs are seeded from that short window every time, so
backtest the vectorbt port on full history.

## Fixes pending in `tv_indicators` (found during this work, not applied yet)

- **HMA:** TradingView's current built-in "Hull Moving Average" (v28, Pine
  v6) uses `math.floor(math.sqrt(length))`. Its old v4 version and our
  `ti.hma` use `round`. They differ when √length's fractional part is ≥ 0.5,
  for example length 14 (4 vs 3), 21 and 34. The 110 strategies that call
  `hma()` would move by a few bars. Hull Suite's EHMA/THMA keep `round`, as
  in that script.
- **ZLEMA lag:** `ti.zlema` uses Ehlers' `(n-1)/2`. Kivanc's widely copied
  `Zlema_Func` (25 strategies) uses `floor(n/2)` and is available as
  `fx.zlema_half_lag`. Add a `lag=` option.
- **`na` inside windows:** Pine documents that `ta.sma`, `ta.highest` and
  similar skip `na` values. Ours return `na` while the window holds one. The
  results are the same unless a series has gaps in the middle.
- **Duplicate names:** three indicators were written independently in two
  staging modules: `EHLERS_SMOOTHED_RSI` and `ERGODIC_MDI` in ehlers and
  hpotter, `TREND_TRADER` in hpotter and trend. The pairs give identical
  output, so keep one of each when merging.
